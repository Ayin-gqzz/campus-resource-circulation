# 低碳校园资源循环流转桌面系统——需求分析文档

## 1. 文档说明

本文依据项目 README、需求清单、架构设计及现有工程结构编写，明确系统的业务目标、功能范围、业务规则、数据需求和验收标准，作为后续设计、实现与测试的依据。

本文描述的是**目标需求，不是整体功能完成证明**。当前仓库已完成 SQLite 建表脚本、领域模型（`domain`）、JDBC 仓储层（`repository`）及 49 个数据层 JUnit 5 集成测试；业务服务层（`service`）和完整业务界面（`ui`）在后续迭代实现。

相关文档：[实验要求与交付清单](requirements.md)、[系统架构](architecture.md)、[数据库设计](../database/README.md)、[测试计划](testing.md)。

## 2. 项目背景与目标

### 2.1 背景及问题

高校学生在学习和生活中会产生闲置教材、学习用品及生活用品。分散的信息发布方式不利于按类别查找物品、跟踪交易意向和保留交接历史，也难以建立统一的评价机制。本项目面向校园闲置资源流转场景，通过结构化的信息管理提高资源利用率，并以有依据的减排系数提供低碳效果估算。

### 2.2 建设目标

1. 建立物品发布、检索、收藏、沟通、交接确认和评价的完整业务流程。
2. 明确学生与管理员权限，防止越权修改和非法状态变更。
3. 持久化业务数据，确保多表操作的一致性及历史记录可追溯。
4. 提供按分类和时间筛选的流转统计、减排估算及 CSV 导出。
5. 在课程规定的三人协作、八周增量开发周期内交付可运行的 Java 桌面软件及配套材料。

### 2.3 系统边界

| 范围 | 说明 |
| --- | --- |
| 运行方式 | 单机桌面应用，通过切换账号在同一应用与本地数据库中操作 |
| 业务对象 | 校园闲置物品，支持售卖和交换 |
| 系统内完成 | 信息发布、意向沟通、流转状态管理、评价、统计与管理操作 |
| 系统外完成 | 售卖付款、实物交接及换物交付 |
| 不作为本期要求 | 在线支付、物流、跨设备实时同步、互联网聊天及自动校园身份认证 |
| 可选扩展 | 本地备份恢复、图片存储、简单推荐及操作日志增强 |

系统内留言属于本地持久化沟通记录，不代表具备联网即时通信能力。低碳数据属于估算结果，不作为实际碳减排认证。

## 3. 用户角色与权限需求

| 角色 | 主要需求与权限 | 限制 |
| --- | --- | --- |
| 未登录使用者 | 注册学生账号、登录 | 不得执行需要身份的业务操作 |
| 普通学生 | 管理自己的物品，检索收藏，参与流转与留言，评价，查看个人历史与统计 | 不得修改他人物品、访问他人私有流转历史或调用管理功能 |
| 管理员 | 学生账号启停、分类维护、违规物品下架、必要的流转取消及全平台统计 | 通过受控本地初始化流程创建，不得由学生注册获得管理员权限 |

除注册、登录外，业务操作应重新核验当前会话、账号状态、角色及资源归属，不得仅依赖界面按钮的显示或隐藏。

## 4. 功能需求

### 4.1 FR-01 账号与权限（对应 R01）

- 支持学生注册、登录和退出；会话仅驻留内存。
- 用户名由 3～24 个英文字母、数字或下划线组成，大小写视为相同；重复注册不得覆盖原账号。
- 密码使用独立随机盐和密码哈希存储，不保存明文密码。
- 密码错误或账号停用时不建立会话，登录失败提供统一提示。
- 普通注册固定分配学生角色；管理员初始化流程须受控。

### 4.2 FR-02 物品管理（对应 R02）

- 发布内容包含名称、分类、描述、成色、标签及流转类型。
- 售卖物品必须填写大于零的价格，金额以整数分存储；交换物品必须填写期望换物说明。
- 发布或更换分类只能使用启用分类。
- 仅发布人可编辑自己的在架物品；存在待处理意向时锁定编辑。
- 发布人可下架在架物品，下架时一并关闭其待处理意向。
- 已完成和已下架记录保留，不以删除历史数据代替状态变更。

### 4.3 FR-03 检索与收藏（对应 R03）

- 支持分类、标题或描述关键词、价格区间的组合筛选和列表展示。
- 仅返回在架且发布人账号启用的物品。
- 价格区间包含边界；指定价格条件时仅返回售卖物品。
- 支持收藏和取消收藏；同一学生重复收藏同一物品只保留一条记录。
- 无匹配结果时展示空列表或明确的空状态，不作为系统故障处理。

### 4.4 FR-04 沟通与流转（对应 R04）

- 非发布人可对在架物品发起意向并附首条留言，两者应原子保存。
- 流转双方可在待处理或已接受阶段追加留言。
- 发布人可接受或拒绝待处理意向，请求人可撤回自己的待处理意向。
- 接受一个意向后锁定物品，同时拒绝该物品其他待处理意向。
- 任一参与人可取消已接受意向，正常取消后物品恢复在架。
- 线下完成付款或换物交接后，由发布人确认完成，同时记录完成时间。
- 双方可查看本人参与的历史及留言；第三方不得查看私有流转记录。

### 4.5 FR-05 评价与信用（对应 R05）

- 仅已完成流转的双方可互评，每方每次流转只能评价一次。
- 评分为 1～5 星，可附短评；被评价人由流转关系推导，不允许任意指定。
- 第三方评价、重复评价、提前评价应被拒绝。
- 信用分为收到的有效评价的算术平均值，保留一位小数；无评价显示“暂无评分”。

### 4.6 FR-06 统计与导出（对应 R06）

- 按完成时间和分类汇总已完成流转数量，未完成或已取消记录不计入。
- 时间筛选采用半开区间，即开始时间包含、结束时间不包含。
- 学生只统计本人参与记录，管理员可统计全平台记录。
- 减排估算量按各分类完成数量乘以单件减排系数后汇总，展示系数来源和未覆盖记录数。
- 无可靠系数的记录不冒充零排放或实际减排，应明确标识未覆盖。
- CSV 使用 UTF-8，正确转义逗号、引号和换行，并防范文本字段公式注入。
- 导出使用页面报告快照，保持筛选条件、权限范围和结果一致。

### 4.7 FR-07 管理功能（对应 R07）

- 管理员可停用、恢复学生账号，维护分类并下架违规物品。
- 停用学生前检查其已接受流转；若存在，应拒绝停用并提示先处理。
- 符合停用条件时，在同一事务内停用账号并取消该学生作为发布人或请求人的待处理意向。
- 停用学生的物品在搜索中隐藏，恢复账号后按物品状态重新显示。
- 管理员可取消已接受流转并下架相应物品。
- 分类停用后禁止用于新发布或更换分类，但保留历史引用。

## 5. 主要用例

| 编号 | 用例及参与者 | 前置条件 | 主流程与结果 | 主要异常 |
| --- | --- | --- | --- | --- |
| UC-01 | 注册与登录：使用者 | 应用正常启动 | 输入合法信息→创建学生账号→验证凭据→建立会话 | 重名、非法输入、密码错误、账号停用 |
| UC-02 | 发布物品：学生 | 已登录且账号启用 | 填写信息→校验分类和交易条件→保存物品与标签→展示在架物品 | 分类停用、价格非法、写入失败 |
| UC-03 | 查找并收藏：学生 | 已登录 | 组合筛选→查看结果→收藏→在收藏列表查看 | 无结果、重复收藏 |
| UC-04 | 完成流转：双方 | 物品在架，请求人不是发布人 | 提交意向及留言→发布人接受→线下交接→发布人确认→保留完成记录 | 已被接受、撤回、拒绝、取消、状态冲突 |
| UC-05 | 互评：双方 | 流转已完成 | 提交星级和短评→保存→更新信用展示 | 越权、重复评价、评分越界 |
| UC-06 | 导出统计：学生或管理员 | 已登录并生成授权范围内报告 | 选择筛选条件→查看汇总及估算→选择路径→导出 CSV | 路径不可写、存储失败、无系数覆盖 |
| UC-07 | 停用账号：管理员 | 目标为学生账号 | 检查进行中流转→取消待处理意向并停用→隐藏相关搜索结果 | 存在已接受流转、权限不足、事务失败 |

## 6. 核心业务规则与状态

### 6.1 状态定义

物品状态：`AVAILABLE`（在架）、`RESERVED`（已锁定）、`COMPLETED`（已完成）、`WITHDRAWN`（已下架）。

意向状态：`PENDING`（待处理）、`ACCEPTED`（已接受）、`REJECTED`（已拒绝）、`CANCELLED`（已取消）、`COMPLETED`（已完成）。

### 6.2 状态转换约束

| 操作 | 意向变化 | 物品变化 |
| --- | --- | --- |
| 提交 | 新建 PENDING | 保持 AVAILABLE |
| 接受 | PENDING → ACCEPTED；其他待处理意向 → REJECTED | AVAILABLE → RESERVED |
| 拒绝或撤回 | PENDING → REJECTED 或 CANCELLED | 保持 AVAILABLE |
| 参与人取消已接受意向 | ACCEPTED → CANCELLED | RESERVED → AVAILABLE |
| 发布人确认完成 | ACCEPTED → COMPLETED | RESERVED → COMPLETED |
| 下架 | 关闭待处理意向；管理员必要时取消已接受意向 | AVAILABLE 或管理员处理的 RESERVED → WITHDRAWN |

同一物品不得同时存在多个已接受意向。完成、拒绝和取消后的意向不得继续追加业务留言。未定义的重新上架、终态恢复等操作不属于当前承诺范围。

接受、取消、完成、下架和停用账号等跨表操作必须在一个事务中提交；权限或状态校验失败、更新行数不符、存储异常时整体回滚，并提示用户刷新或重试。

## 7. 数据需求

| 数据对象 | 核心内容 | 完整性要求 |
| --- | --- | --- |
| 用户 | 用户名、密码哈希、角色、启用状态 | 用户名大小写不敏感唯一，角色受限 |
| 分类 | 名称、启用状态、减排系数及来源 | 系数与来源配套，停用不破坏历史引用 |
| 物品与标签 | 发布人、分类、描述、成色、交易类型、价格或换物意向、状态、标签 | 金额整数化，引用有效，状态合法 |
| 收藏 | 用户与物品关联 | 同一用户和物品组合唯一 |
| 流转意向 | 物品、请求人、状态、完成时间 | 状态与完成时间一致，防止重复接受 |
| 留言 | 流转记录、发送人、内容、时间 | 发送人必须为参与者，受流转阶段约束 |
| 评价 | 流转记录、评价人、被评价人、星级、短评 | 每方每次流转一次，星级 1～5 |

业务数据通过 SQLite 与 JDBC 持久化；重新启动后应能查询已提交数据。时间统一采用 UTC 存储。历史记录及引用关系应保留，数据库约束用于兜底，但不能替代服务层权限与流程校验。

## 9. 验收与需求追踪

| 需求 | 关键验收场景 |
| --- | --- |
| FR-01 | 大小写不同的重名注册被拒绝；错误密码和停用账号不能登录；持久化数据不含明文密码 |
| FR-02 | 非本人不能编辑；待处理意向锁定编辑；下架连带关闭意向；非法价格不落库 |
| FR-03 | 组合筛选结果正确；价格边界包含；停用发布人和非在架物品不出现；收藏去重 |
| FR-04 | 接受一个意向后拒绝其他意向；取消恢复在架；完成同步状态与时间；失败时无部分提交 |
| FR-05 | 只有完成后的双方可各评一次；星级越界被拒绝；平均值和无评分展示正确 |
| FR-06 | 权限及时间边界正确；未完成记录不计入；无来源系数不参与估算；CSV 与页面一致且安全转义 |
| FR-07 | 学生不能管理；存在已接受流转时不能直接停用；分类停用后保留历史 |
| NFR-01～08 | 完成界面演示、安全检查、事务测试、部署验证及测试和日志材料检查 |

验收记录应包含测试环境、输入数据、预期结果、实际结果与证据。编译成功、存在接口或测试代码，均不能替代业务验收。

## 10. 风险与待确认事项

1. **安全方案**：密码哈希算法、参数、密码长度规则及首个管理员初始化方式尚需明确。
2. **输入边界**：名称、描述、标签、留言和短评的长度上限及空白处理规则需统一。
3. **低碳估算**：系数来源、单位、版本管理以及系数变更对历史报表的影响需评审；当前设计按当前分类系数汇总，不应声称已冻结历史系数。
4. **本地数据风险**：数据库文件损坏或误删可能导致数据丢失；备份恢复属于可选扩展，应在部署说明中提示风险。
5. **实现进度风险**：已有数据层不代表业务服务与图形界面完成；应按注册发布、检索流转、评价统计、管理交付逐步形成可演示闭环。
6. **范围控制**：新增联网、多端同步或在线支付会显著改变架构，应单独评审而非默认纳入本期。

最终交付包括完整 Maven 源码工程、SQLite 初始化脚本、JUnit 用例、可执行 Jar、部署与使用说明、课程设计报告、UML 图、测试与重构证据、真实协作记录以及演示材料。开发按八周、每两周一个迭代版本组织，详细计划以 [迭代计划](iterations.md) 为准。
